# End-to-end encryption for what people write

Status: accepted 2026-10-29 ([D24](https://files.schnau.dev/html/studienbuch-roadmap/#D24), [D38](https://files.schnau.dev/html/studienbuch-roadmap/#D38))

Everything a person writes is sealed on their device: homework, grades, absences, signatures, photos and the profile with the display name, and later every shared space. The server stores an envelope and a ciphertext and can't read either. School data and `Enrollment` stay readable, because the server imports the first and routes lessons by the second. A leaked dump like the one in 2026 then holds no grades, absences or names, and the server still enforces membership, roles, key epochs and signatures.

A sealed row is AES-256-GCM under its space's key of the current epoch. The plaintext carries the table name and the row's JSON, padded to a power of two from 1 KiB, so the server can't tell a grade (about 270 bytes) from short homework by size. That costs about 3 MB on the server for a 3,000-row notebook. The envelope holds a format version, a suite id, the key epoch and the author. The associated data binds the ciphertext to its space, row id, key epoch and author, so the server can't move it to another row or pass it off as someone else's. A new primitive gets a new suite id, and a new layout a new format version, so stored rows never migrate. An older app parks a row whose format or suite it doesn't know until it updates. The layouts and their vectors live in `packages/e2ee`.

The associated data binds no row version, so a server can serve an older ciphertext of a row as if it were current, for example to undo a "done" or bring back a deleted homework. We accept this. The device seals before the server assigns a version, so only the base version could be bound, which helps only a device that already holds a newer copy of that row and constrains how commands batch. A restore (ADR 0021) rolls rows back on purpose, so devices have to accept older states anyway. A server that serves a whole older space, or withholds new writes, can't be caught by anything bound per row. And the attacker who would do this is an active operator, who can also ship a modified app (`encryption.md`, section 1). The device therefore does nothing extra and shows what the server serves; after a real restore, the restore epoch's re-push brings back what it wrote in the last seven days. Detecting a rollback needs signed space heads or key transparency, which a later envelope format can add.
