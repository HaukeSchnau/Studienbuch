# Accounts without an email address

Status: accepted 2026-11-17 ([D97](https://files.schnau.dev/html/studienbuch-roadmap/#D97))

An account needs no email address. Sign-up offers two ways in: the email account as before, and an account without an address, which starts with a passkey, or with the Notfallkarte on a device without passkeys. The Notfallkarte alone then signs in to such an account: the device derives a login from the card's 128 bits (`RecoveryCode.login`), and the server keeps only its SHA-256 as a Better Auth account row. Whoever holds the card holds the account and the notebook, as with a recovery phrase. So a new card retires the old one's login and wrappers, and signs out every other session of the account, as a new password does: whoever found the old card may have signed in with it. An email account's card still opens only the notebook, after a sign-in, and a new card retires its old one's wrappers too, so a lost card stops working for every account. The server remembers a digest of a retired card's public key, so a device that resends it after a lost answer can't make it the card again. A new card waits on its device from before its request until the student saved it, so a lost answer never leaves the account with a retired card and a new one nobody saw. A public computer keeps that card in the tab's memory only: closing the tab after a lost answer, before the code shows, loses the new card while the server may already have retired the old one. A public computer keeps a new account's card and session in the tab's memory only, not in sessionStorage: browsers restore a closed tab's sessionStorage when someone reopens it, which on a school computer would hand both to the next person. A reload there before the card is saved costs the new, empty account and the code's use, and the page warns first. A new account's card reaches the server with its login as soon as the account's first device has the notebook's key, while the sign-up is fresh, so the card works even if that device is gone before the student finishes the card step. A card-first sign-up stages its card beside the device's sessions before its request goes out, and a device keeps a new session only once the account's secrets hold its card. A device that can't store the card stops there and says so, so neither a lost answer nor a restart loses an account's only way in. A kept session or a sign-out removes the staged card, so the next sign-up on the device doesn't find it. That removal is best effort once the session is kept: if the keychain refuses, the failure is logged, and the next start or sign-out removes the card. A card that signs in on the account's first own device stays with that device the same way until the server holds its wrapper. One step at a time per account makes and resends the first key and puts the card to work, so two steps can never make two keys. One sign-in, sign-up or "Kurz bestätigen" runs at a time per device, and no request of one waits longer than 30 seconds for its answer: one that doesn't come by then counts as lost. Sign-out never waits for one: it takes over while it forgets the account, and a sign-in that began before it keeps no session when its answer comes, and ends that session on the server, so a hanging request can neither block sign-out nor sign the student back in. Then sign-out ends on the server the session it erased, while the next sign-in may already run. The turn that keeps its session checks who holds the device and fixes where the session goes, and the card goes there too, so two sign-ins never both keep a session and a public computer's card never lands on disk.

Better Auth needs an address per account, so an account without one carries Better Auth's placeholder under `.invalid`, made from a random id. `Mail` refuses any `.invalid` recipient and no email route accepts one, so nothing mails a code a stranger could use. A passkey that signs up registers without a session, which this ADR adds to [ADR 0025](0025-recovery-without-escrow.md): it needs an access code's reservation, and the account, the passkey and its session come into being in one transaction. A registration from a signed-in device keeps ADR 0025's ten-minute rule and still signs nobody in. Nobody confirms such an account, so its sign-up takes the code's use before the account exists, and every code has a use limit. A code then makes no more accounts than it has uses.

The LfD Niedersachsen's Eckpunkte for learning platforms want pseudonymous pupil accounts to be possible, and the address is the most identifying thing the server reads about a pupil. Passkeys alone would leave the login without a way back once the passkey is gone, and school computers without a way in. School-issued IDs need a school, which D96 rules out as the only way in, and bring passwords back. What this leaves out: adding an address to an account without one, and deleting accounts nobody signed in to for 13 months, which needs in-app deletion first.
