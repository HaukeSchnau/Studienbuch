Studienbuch,
drawn out

The rewrite as it stands on main: where each part lives, what talks to what, and how a single line of homework travels from one phone to another without the server ever reading it.

Drawn from the code at ed883cd on 11 November 2026, not from the design docs. Hover a box to see its connections, click it for what it does and where it lives. Dashed boxes with a milestone aren't built yet; the switch "Only what's built" fades them.

1The whole system

Everything runs as one Node process per environment. Beta and up to three previews live on srv-2 behind Caddy, each started by the service controller with its own Postgres database. A phone, a browser tab and the landing page all talk to that one origin. Calder builds and deploys; nobody changes srv-2 by hand.

Previews (pr-N.studienbuch.schnau.dev) are Tailnet only. Beta (beta.studienbuch.app) is public. Dev is the same server on localhost, proxying Vite and Metro.

3Inside the app

Directories answer why code exists. Routes are shaped by Expo Router, features by the domain, and everything that exists because of a technology sits in src/infra. Screens read atoms, atoms run on a runtime built from layers: one set per device, and one more per signed-in account with its own database, secrets and sync engine.

Platform differences live in .web.ts(x) twins, mostly in infra, and in one .native.tsx (the Sync Lab's route). Each adapter box lists the native answer first and the browser's second.

4Inside the server

One Effect process serves four kinds of traffic: Effect RPC at /api/rpc, Better Auth at /api/auth, the sync socket at /api/sync, and the web builds. The same bundle is also the CLI: prepare migrates before traffic switches, console holds operator commands, verify checks invariants.

5A write, end to end

Every write starts the same way: the mutator from packages/core runs on the device, the row and the command land in SQLite in one transaction, and the screen updates before any network. The two paths split at the push. A readable command carries the mutator's arguments and the server runs the mutator again, so it can refuse. An encrypted command carries the sealed result, and the server checks only what it can see.

Scroll the diagram sideways.

Only enrollment.set takes the readable path today, because the server derives course memberships from it. homework.* and notebookProfile.set take the encrypted path.

6Encryption: keys and wrappers

One root key R per account sits in the device's keychain. Everything else hangs off it: an identity key that signs, a sealing key that opens key boxes, and a key per space and epoch that encrypts rows. The server keeps public keys, signatures and ciphertext. To reach R on a new device, R is sealed to "wrappers": this device, a passkey's PRF output, or the Notfallkarte. There is no escrow: lose every wrapper and the notebook is gone.

Scroll the diagram sideways.

Suite 1: AES-256-GCM, HKDF-SHA256, X-Wing (hybrid post-quantum KEM), Ed25519, SHA-256. Every format records its suite id, so a new primitive is a new id and stored data never migrates.

7Spaces and membership

Every synced row lives in exactly one space, and membership is the only read rule: a device pulls every space its account belongs to, and nothing else. Today there are three kinds. The school space is readable and written only by the server. Each student's notebook is sealed and owned by that student. Course spaces exist so a course choice decides who receives its lessons.

9A device's life

Offline is a normal state, and so is a session that ended: the device keeps its data and its outbox and waits for the same account to sign in again. The only ways to lose local data are signing out (which now warns about unsent changes) and, from M3, being removed by another device.

10From commit to phone

A pull request gets a preview as soon as the bundle passes its smoke test, before the other checks finish, so Hauke can look early. A push to main deploys to beta only after every check. The native path is configured but not connected: EAS profiles and channels exist, no CI job calls them.

14How it's tested

16Where the code and the docs disagree

The diagrams above follow the code. These are the places where a design doc, an ADR or AGENTS.md says something else, most misleading first.

  • The pull carries no account-key news.architecture.md and sync.md say the pull returns keys {generation, alerts} and a device picks up a renewed key through myDeviceSeal. Neither exists. The pull does carry each sealed space's current key epoch and its key boxes as _key rows, but a device learns about the account's root key only from the push answers NoKeyRecord and KeysBehind.packages/sync/src/protocol/Protocol.ts
  • Four key calls, not eight.recovery.md, domain.md and encryption.md list rotate, revokeDevice, reset, myDeviceSeal and pairing.* with a pairing_session table. The code has state, init, addWrapper and fetchSeals; key_wrapper has no place, revoked or last-fetched columns, and a device wrapper is tied to a session.packages/api/src/Keys.ts, apps/server/src/keys/KeyTables.ts
  • The sync tables look different.sync.md's diagram gives space columns such as school_id, floor, history, rotation_required; space_member.user_id; sync_client.revoked_at; command_log.args and outcome. The code has (id, kind, parent_id, key, version, key_epoch), account_id with granted_by, and kind, detail, applied, sha256. A space kind says whether it may hold sealed rows, and each table declares itself readable or encrypted, so a notebook holds both.packages/sync/src/server/Tables.ts
  • Nobody sends DeviceRevoked.sync.md and ADR 0017 describe a removed device wiping itself on Sync.DeviceRevoked. The client handles it; the server never sends it, and Sync.Locked is likewise declared but unused. Both wait for M3's device removal and later confirmations.packages/sync/src/client/Replication.ts, packages/sync/src/server/SealCommand.ts
  • Restores don't resend key operations.ADR 0021 and architecture.md invariant 12 say devices re-send their key operations of the last 7 days after EpochChanged. ADR 0025 names ADR 0021 and says M1 doesn't, because a re-sent passkey or card wrapper would fail the ten-minute rule; the code only republishes generation 0 and the device wrapper on NoKeyRecord. ADR 0021 now says at its top that 0025 supersedes that part. The rest of 0021 holds: the device forgets its cursors and the next pull replaces every space.packages/sync/src/client/Replication.ts, apps/app/src/features/keys/KeysState.ts
  • No tombstone floor, no engine jobs.sync.md plans a tombstone floor, a purge job and a daily membership job for term dates. The only job is heartbeat, and the course rule ignores dates until M3.apps/server/src/infra/jobs/Jobs.ts, packages/core/src/notebook/Enrollment.ts
  • The access flow is shorter.domain.md has access.reserve(code) then access.redeem(reservation). The code has one Access.redeem({code}) that returns a reservation; the sign-up carries it in a header and confirming the email admits.packages/api/src/Access.ts, apps/server/src/auth/Auth.ts
  • The profile mutator changed.domain.md's notebook.update(cohortId?, adult?, displayName?) is notebookProfile.set(notebook, displayName, adult). The server-written Notebook row and the separate CourseOffering table aren't in domain.md.packages/core/src/notebook/
  • Space keys live in SQLite.encryption.md keeps them in a space_key table and deletes them from the keychain at logout. They are in sync_space_key in the account database.packages/sync/src/client/EngineTables.ts
  • Account deletion doesn't exist.Several docs describe account.delete crypto-shredding the account. Better Auth's /delete-user is disabled and there is no other path.apps/server/src/auth/Auth.ts
  • architecture.md is ahead of the code.It describes the WebUntis import, Lesson, ImportStatus and blobs in the present tense. There is no import code, and no server code reads the blob buckets.apps/server/src/main.ts
  • Hosting details drifted.hosting.md puts the R2 bucket in the Studienbuch stack (infra's tokens stack makes it), removes previews after 7 idle days (only closing the PR does), lets the preview wait on the bundle (it waits on serverSmoke) and grants 6 services (4). ADR 0010 says there is no separate tsc run; CI runs tsc --noEmit..calder/ci.ts, deploy/alchemy.run.ts

17Worth your attention

Things I found surprising while reading, with what I'd do about them.

  • On the web, space keys sit unencrypted in OPFS.The root key and device seed are sealed under a non-extractable WebCrypto key in IndexedDB, but sync_space_key is a plain blob in the account's SQLite, which the browser keeps unencrypted. The opened rows sit in the same file as plaintext in base_row, so a copied browser profile already reads today's notebook; the keys add every row written later, because key rotation isn't built. Wrapping the space keys the way the root key is wrapped would close the second part only. The first needs the browser's database itself encrypted.
  • The simulation never seals.It runs with sealing = false, so the engine's own encrypted path (sealing at push, Stale and re-seal, opening on pull) isn't exercised there, and the plaintext invariant only ever sees forged markers. The flag's comment still says the engine sends no Seal yet, which stopped being true when Sealing.ts landed. The encrypted path is the one that matters most for privacy.
  • Browser tests and E2E don't run in CI.The four Playwright browser tests run only locally, and no E2E runner exists yet although 74 scenario contracts are accepted. The CI shell already has Playwright's Chromium and Firefox (flake.nix, since 29 October); test-app in .calder/ci.ts still excludes *.browser.test.ts with a comment saying the shell lacks them. Dropping that exclusion, or adding a browser job, is the first step.
  • Some security state lives only in memory.Rate limits and session revocations are per process. A restart clears every limit. A second server process would miss revocations, so a revoked session's sockets there stay open until that connection checks its session again, 4 to 6 minutes later.
  • Deleting an account would leave ciphertext behind.space_member, sync_client, command_log and notebook spaces have no foreign key to auth_user. Deleting a user cascades the auth, access, demo and key tables: sessions and keys go, while the notebook space, its ciphertext and key boxes in sync_row, the memberships and the command log stay. Worth deciding before the first real deletion request.
  • Provisioned, unused.Garage and R2 buckets exist in every environment with credentials in the process, and no code reads them until M4. The heartbeat job runs on every preview because STUDIENBUCH_JOBS is never set.
  • Probing seal fetches is free.fetchSeals counts only fetches that found seals. Probing unknown credential ids costs nothing, though it also returns nothing.

Ideas

  • Turn sealing on in the simulation first.It's the cheapest large gain in confidence: the machinery is there, one flag and the Planner's Note steps away.
  • Keep this atlas honest with a check.Every file path on this page is a link. A small script in CI that fails when a linked path stops existing would catch most drift, and the boundary table in section 2 could be generated straight from import-boundaries.ts.
  • Show the user what the server sees.Section 12 is close to a screen Studienbuch could ship: "Was der Server von dir weiß", listing email, Kurswahl, spaces and times, with everything else marked as encrypted. It turns the privacy claim into something a parent can check.
